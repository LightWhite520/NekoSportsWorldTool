# 配速单位修正（7.4.0）

2026-11-02 的官方 App 7.4.0 截图显示：1 公里用时 06:42，分段配速却为 402′00″；下一公里用时 06:41，配速为 401′00″。全程平均配速约 6′42″，曲线却在 9′00″ 附近，起步显示“最快 2′20″。

已核对用户运行的 Windows EXE 与 `integrated-preview-20261102` 发布包中的 EXE SHA-256 相同；ADB 确认官方 App 为 7.4.0（versionCode 408）。

## 原因与修正

| 字段 | 原输出 | 修正后的单位 |
| --- | --- | --- |
| OBS `laps_json[].avgPace` | 秒/公里，例如 402 | 十进制分钟/公里，例如 6.7 |
| OBS 轨迹点 `speed` | km/h，例如 8.9552 | 十进制分钟/公里，例如 6.7 |
| 记录级 `speed` | 千分之一分钟/公里，例如 6700 | 保持原单位 |
| 内部 `GenPoint.speed` / OBS `bdS` | km/h / m/s | 保持原单位 |

配速在 OBS 序列化边界转换；不改变运动模型、轨迹坐标、距离积分、时长、步频或步数。分段配速保留四位小数，避免两位小数造成最高 0.3 秒的量化误差。零速度继续输出零值；零时长分段配速继续为 null，不生成无穷大。

使用原发布 EXE 的离线 `motion-check --distance 2090 --duration 840 --seed 7 --timeline` 得到 841 个样本。稳定速度约 8.9783 km/h，对应配速约 6.6828 分钟/公里；首个移动样本为 0.65 m/s，即 2.34 km/h。把 2.34 当分钟格式化即约 2′20″，与截图吻合；真实瞬时配速应约为 25′38″。这也解释了为何减速在旧图上表现为加速。

每公里分段配速应分别显示为 6′42″、6′41″。尾段应按未舍入距离计算，不能直接用界面显示的 0.09 公里推导精确配速。

## 证据与限制

此前根据另一张旧截图将分钟改为秒，仅为未经客户端验证的推断；当时测试也固化了同一假设。本次更正该判断，回归测试解码实际 gzip/base64 OBS，覆盖截图数值、完整公里、半公里、短尾段、跨公里插值，以及起步/稳定/减速/停止时的曲线字段。

离线验证：`cargo test --lib --no-default-features --locked --offline track::` 通过 41 项；`cargo test --lib --no-default-features --locked --offline api::submit::metric_tests` 通过 1 项。测试只运行所列模块，不读取账号配置。

ADB 可提取安装包，但应用不是 debuggable，无法通过 `run-as` 读取私有运动数据库；检查到的当日日志不含配速或轨迹字段。JADX 1.5.6 只能看到网易加固壳，尚未取得业务层配速格式化代码。结论依据是截图、发布二进制复现及本工具源码，不能表述为已反编译确认客户端实现。

没有读取用户禁止的两个配置文件，没有重新提交成绩，也没有验证修正后的官方 App 显示。已有服务器记录不会被本地修改自动更新，其他客户端版本的字段兼容性未验证。
